## 一、缺陷总览

| 风险等级 | 数量 | 定义 |
|---|---|---|
| **高** | **6** | 造成功能完全不可用、权限泄露、数据假象 |
| **中** | **6** | 部分功能失效（如按钮点击无效果）、状态机漏洞、静默降级 |
| **低** | **6** | 体验优化、代码卫生、一致性问题 |
| **合计** | **18** | |

**最需优先处理的 3 条**：
1. 后端 `/api/competitions` 写接口无角色限制 → 任意登录用户可增删改赛事（越权）
2. 登录为纯前端 Mock + 硬编码密码 → 任何人可用 `admin123` 进管理后台（认证形同虚设）
3. 竞赛列表 / 观众中心状态筛选枚举不匹配 → 点击筛选后列表必然全空（功能完全不可用）

## 三、补充后的需求片段

> 以下内容可直接补入需求/设计文档，用于消除上述缺陷对应的规则缺失。

### 3.1 权限与访问控制规则（补齐）

**R1 角色与页面归属矩阵**（必须同时满足前端隐藏与后端校验）

| 页面/模块 | 允许角色 | 无权限访问时行为 | 后端校验要求 |
|---|---|---|---|
| `/admin-dashboard`、`/admin-scoring`（管理后台全部功能） | 仅 admin | 前端隐藏入口；直接输入 URL 跳转首页；接口返回 403 | 所有 `/api/admin/**` 需 `ROLE_ADMIN`；**新增：赛事创建/编辑/删除必须校验 ADMIN** |
| `/expert-review`（专家评审） | 仅 expert | 跳转首页并提示"无权限" | 所有 `/api/expert/**` 需 `ROLE_EXPERT`；**新增：评分接口需校验赛事状态与评分窗口** |
| `/my-submissions`、`/player-center`、`/hackathons/:id/register` | 仅 player | 跳转登录页 | 需 `ROLE_PLAYER`；操作资源前校验归属（当前 service 层已实现，保持） |
| `/`、`/hackathons*`、`/leaderboard`、`/viewer-center` | 公开 | — | GET 只读，permitAll |
| 点赞、评论 | 登录用户 | 未登录点击 → 弹登录引导 | POST 需 authenticated |

**R2 认证规则（新增）**
1. 登录必须调用后端 `POST /api/auth/login`，成功后后端返回 JWT，前端存储 token 并在每次请求注入 `Authorization` 头。
2. 用户角色**以后端 JWT claim 为唯一真相源**，前端不得本地判定角色、不得硬编码任何账号密码。
3. 后端 JWT 过滤器需回查数据库校验用户角色与启用状态；用户被降权/禁用后，其 token 立即失效（或引入 token 吊销机制）。
4. 注册接口固定角色为 `player`（已实现），管理员/专家账号只能由管理员后台创建（已实现）。

**R3 后端鉴权加固（新增）**
1. 启用 `@EnableMethodSecurity`，所有写操作（POST/PUT/PATCH/DELETE）方法级标注 `@PreAuthorize`。
2. `anyRequest()` 默认策略改为 `denyAll()`，杜绝"新接口忘记挂前缀即裸奔"。
3. 所有涉及资源 id 的操作，service 层必须校验资源归属或操作者权限（现有 SubmissionService/TeamService/CommentService 已实现，需覆盖到 Competition 相关操作）。

### 3.2 交互动作完整性规则（补齐）

**R4 筛选与搜索组件**
1. 筛选控件的候选项 value 必须与数据状态枚举严格一致，禁止使用展示文案（如"进行中"）作为值、禁止 `as any` 强转绕过类型检查。
2. 状态枚举统一定义为：`registration_open`（报名中）、`competition_running`（进行中）、`results_announced`（已公示）、`draft`（草稿）、`ended`（已结束），前后端与数据库保持一致。
3. 每个筛选项必须有验收用例：选择该条件 → 列表非空 → 结果中每条数据的状态均等于所选值。

**R5 提交类操作的完整反馈**
1. 所有提交（报名、提交作品、评分、发布公告、保存配置）必须定义四态：提交中（按钮禁用+loading）、提交成功（明确成功提示+后续动作）、提交失败（展示后端返回的具体错误原因，保留用户已填数据）、网络异常（提示"网络异常，请重试"并提供重试入口）。
2. **禁止"静默成功"**：不得在后端调用失败、跳过、未执行的情况下展示成功状态。
3. **禁止"静默失败"**：接口失败必须给用户可见反馈，不得仅 `console.warn` 后回退 mock 数据。

**R6 三态规范**
所有列表与详情区域必须定义并区分：
- 加载中：骨架屏或 loading 提示
- 空数据：明确的空状态插画 + 文案（如"暂无符合条件的竞赛"）
- 请求失败：错误提示 + 重试按钮（与空数据视觉上明确区分）

### 3.3 业务状态机规则（补齐）

**R7 赛事生命周期与操作窗口**

| 赛事状态 | 允许报名 | 允许提交作品 | 允许专家评分 | 允许改分 |
|---|---|---|---|---|
| 报名中 registration_open | 是 | 是（报名通过后） | 否 | 否 |
| 进行中 competition_running | 否 | 是（截至 submit_end） | 是 | 是（窗口内） |
| 已结束 ended | 否 | 否 | 是（评分窗口内） | 否（超出评分截止） |
| 已公示 results_announced | 否 | 否 | 否 | 否 |

后端须在每个写操作前校验当前时间与赛事状态，不满足时返回明确错误码与文案，前端展示该文案。

### 3.4 验收标准（可逐条验证，补齐）

**A1 权限验收**
1. 使用 player 账号登录后，直接访问 `/admin-dashboard` → 页面跳转且接口 `/api/admin/**` 返回 403。
2. 使用 player 账号登录后，调用 `POST /api/competitions` → 返回 403（当前为允许，修复后验证）。
3. 使用 `admin@hackathon.com / admin123` 登录 → 登录失败（当前为成功，修复后验证）。
4. 管理员在后台将某用户角色改为 player 后，该用户刷新页面 → 管理入口消失且接口返回 403。

**A2 筛选验收**
1. 竞赛列表页依次选择"报名中/进行中/已公示" → 每次列表均**非空**，且结果中每条赛事状态与所选一致。
2. 观众中心依次点击"进行中/即将开始/完赛回顾" → 每次作品区**非空**，且作品所属赛事状态与所选一致。
3. 搜索框输入存在的关键词 → 列表收敛；输入不存在的关键词 → 展示空状态文案，而非空白页。

**A3 提交闭环验收**
1. 断开后端服务后提交报名 → 页面显示明确失败提示，**不得**显示"报名成功"。
2. 提交作品但未通过报名审核 → 点击提交后显示"报名尚未通过审核"，而非无反应。
3. 报名成功后，管理员在报名审核列表可见该条待审记录（前后端数据一致）。

**A4 数据一致性验收**
1. 提交作品后刷新页面 → 作品仍在列表中（localStorage 持久化，已实现）。
2. 换浏览器/清除缓存后 → 明确提示本地演示数据会丢失（需产品确认是否接受）。
3. 管理员修改赛事结束时间后重开页面 → 修改保留（已实现）。
